## Problem Statement

**The pain**: [Describe the specific friction or failure mode — not a feature request, not a solution. What is breaking or missing for the user?]

**Who feels it**: [Specific role. Not "users." Not "customers." The person in the moment — e.g., "an engineering manager looking at Monday's digest with three overdue action items and no idea which to address first."]

**Evidence**: [Quantitative data, user research quotes, support tickets, session recordings — something external to your opinion. If you only have a hypothesis, say so and flag it as a risk.]

> **Common mistake**: "Users want X" is not a problem statement. It's a solution hypothesis dressed up as a problem. Start with the pain, not the ask.

## User Stories

Format: **As a [specific role], I want [action], so that [measurable outcome].**

The "so that" is not optional. If you can't state the measurable outcome, you don't understand why the story exists.
