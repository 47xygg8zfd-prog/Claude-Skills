## P0 Additions — Not in Spec

These scenarios address systemic risks not covered by the happy-path spec.

### P0-A: Race Condition — Two Engineers Paged Simultaneously for Same Alert

**Risk**: Routing engine reads incident history to compute suggestion. If two incidents of the same alertType are created within milliseconds, both reads happen before either is written. Both suggestions could resolve to the same engineer, ignoring load.

**Given**: Two PagerDuty webhooks arrive within 200ms for incidents of `alertType=payment-timeout`.  
**When**: The routing engine processes both in parallel.  
**Then**: Each incident receives a routing suggestion computed correctly; suggestions may match (acceptable) but neither suggestion should be based on stale/missing history; no DB constraint violation; no 500 error in either webhook response.

| Field | Value |
|-------|-------|
| Priority | P0 |
| Precondition | Routing engine deployed; DB seeded with history for payment-timeout |
| Test Data | Two PD webhook payloads with identical `alertType`, different `incidentId`, timestamps 150ms apart |
| Automate | Yes — integration test with concurrent HTTP calls |
| Pass Criteria | Both incidents created; both have valid `routingSuggestion` or explicit null; no 5xx; no duplicate incident IDs |

---

### P0-B: Runbook Capture When Incident Service Is Down at Webhook Time

**Risk**: PagerDuty fires webhook; incident service is temporarily unavailable (deploy, crash). Webhook drops. Incident never enters system. Engineer never gets routing suggestion or runbook prompt.

**Given**: PagerDuty webhook fires for a real incident.  
**When**: The incident service is returning 503 at the time the webhook arrives.  
**Then**: The webhook is queued (not dropped); incident is created when service recovers; engineer is notified; no incident is silently lost.

| Field | Value |
|-------|-------|
| Priority | P0 |
| Precondition | Webhook ingestion queue configured (SQS or equivalent); incident service can be toggled down in staging |
| Test Data | PD webhook payload; simulate 503 for 60 seconds, then restore service |
| Automate | Yes — integration test in staging; mock service unavailability with network intercept |
| Pass Criteria | Incident appears in feed within 120s of service recovery; no data loss; queue depth metric visible |

---

### P0-C: Engineer Tries to Close Incident Without Writing Runbook — Modal Must Block

**Risk**: Frontend blocking logic has a gap. Engineer finds a path to close the incident (browser back, direct API call, session timeout exploit) that bypasses the modal.

**Given**: An incident in `acknowledged` state.  
**When**: The engineer attempts to close the incident via any of the following: (a) clicking Close Incident normally, (b) pressing ESC after clicking Close, (c) using browser back button during modal, (d) calling `POST /api/incidents/:id/close` directly without a `runbookId` or `skipReason` in the request body.  
**Then**: (a–c) Modal remains open, incident not closed; (d) API returns `400 Bad Request` with error code `RUNBOOK_OR_SKIP_REQUIRED`.

| Field | Value |
|-------|-------|
| Priority | P0 |
| Precondition | Active incident in `acknowledged` state; frontend and API both deployed |
| Test Data | Standard active incident |
| Automate | Yes — E2E (paths a–c) + API test (path d) |
| Pass Criteria | All four paths fail to close the incident without runbook/skip; incident remains `acknowledged`; no silent success |

---

### P0-D: HDI Calculation When Engineer Is Removed from Team Mid-Period

**Risk**: Engineer leaves team or is removed from the on-call rotation mid-measurement period. Their historical incidents are attributed to them but they're no longer in the team roster. HDI denominator is unclear. Dashboard may crash or show nonsense.

**Given**: Engineer A handled 8 incidents in the last 30 days. On day 20, Engineer A is removed from the team in the system.  
**When**: An engineering manager views the HDI dashboard for the last 30 days.  
**Then**: Engineer A's incidents are still counted in the HDI calculation for the period they were on the team; dashboard does not crash; Engineer A appears in the breakdown table labeled "(removed)" or equivalent; HDI percentage is mathematically correct.

| Field | Value |
|-------|-------|
| Priority | P0 |
| Precondition | Engineer with incident history exists; admin can remove engineer from team mid-test |
| Test Data | Seed 30 days of incidents; remove engineer on day 20 |
| Automate | Yes — integration test; seed DB, fire remove action, assert HDI API response |
| Pass Criteria | HDI correct; no 500; removed engineer visible in breakdown with clear label; historical data not deleted |

## P1 Additions — Edge Cases and Boundary Conditions

### P1-A: Runbook Search with Special Characters

**Scenario**: Engineer types `"connection refused (errno: 111)"` or `logs show 'NullPointerException @ com.sentinel.Foo:42'` — special characters that could break query parsing or SQL injection vectors.  
**Expected**: Search handles gracefully; no 500; returns relevant results or empty state; no SQL injection possible.  
**Automate**: Yes (unit test on search input sanitization + API integration test).

### P1-B: Very Long Runbooks (>10,000 characters)

**Scenario**: Engineer pastes a comprehensive 15-step runbook including code blocks, totaling 12,000 characters.  
**Expected**: API accepts it (confirm max payload limit is ≥15K chars); stored correctly; retrieved and rendered without truncation or layout break; pgvector embedding generation completes within 5 seconds.  
**Automate**: Yes (API test with oversized payload).

### P1-C: First-Time User — No Routing History

**Scenario**: New Sentinel customer with zero prior incidents in the system. First incident fires.  
**Expected**: Routing suggestion renders as null with "No routing history yet — assigning to on-call primary"; no JS error; no empty crash in HDI dashboard (shows "Not enough data yet — check back after 10+ incidents").  
**Automate**: Yes (E2E with clean-slate DB).

### P1-D: Skip Reason `runbook_in_progress_will_add_later` — Follow-up Flag

**Scenario**: Engineer selects "I'll add it later" as skip reason.  
**Expected**: Incident closes; DB records `skip_reason = runbook_in_progress_will_add_later`; follow-up reminder Slack message sent to engineer 24 hours later; reminder links back to the incident.  
**Automate**: Partially — unit test for follow-up scheduler trigger; E2E in staging to verify Slack message fires (manual verification of Slack message content).

### P1-E: HDI Dashboard — Custom Date Range Spanning >90 Days

**Scenario**: Manager selects a custom range of 180 days.  
**Expected**: System either (a) accepts and computes correctly for full range, or (b) returns a clear error "Maximum range is 90 days. Contact support for longer-range exports." No silent data truncation.  
**Automate**: Yes (API test + component test).

## Test Infrastructure Notes

- **API mocking**: MSW (Mock Service Worker) for all frontend unit/component tests
- **E2E framework**: Playwright; tests run in CI on every PR to `main`
- **Staging environment**: Mirrors production DB schema; seeded with anonymized fixture data; PagerDuty sandbox account connected
- **Chaos testing**: Conducted manually in staging by QA lead; script-driven service outage simulation
- **Accessibility testing**: axe-core automated + manual screen reader walkthrough (VoiceOver + NVDA) before launch
- **Performance baseline**: Lighthouse CI on each PR; HDI API response times tracked in Datadog
